# Правила работы с репозиторием

## Перед изменениями

1. Прочитать `docs/README.md` и `docs/spec/MVP_SPEC.md`.
2. Открыть тематический документ, который является источником истины для
   изменяемого поведения.
3. Проверить `docs/spec/OPEN_QUESTIONS.md`: нерешенный вопрос нельзя молча
   превращать в бизнес-правило.
4. При работе по roadmap прочитать раздел соответствующего этапа, persistent
   handoff предыдущего этапа и обновлять
   `docs/implementation/handoffs/stage-NN.md`.

Границы этапов заданы в `docs/implementation/ROADMAP.md`. В локальной рабочей
копии могут находиться игнорируемые Git операционные промпты, но они
необязательны для реализации, не являются источником истины и не должны
подменять спецификацию, тематические документы или roadmap.

## Данные и безопасность

- Не коммитить `.accdb`, `.mdb`, клиентские `.xlsm`, исходные Office-шаблоны и
  выгрузки с PII/служебными metadata, секреты и сгенерированные import
  artifacts. В Git допускаются только обезличенные профили и manifest/README
  источников.
- Не открывать клиентские Office-файлы через Excel/COM/LibreOffice и не
  исполнять embedded VBA/macros. Разрешён только неисполняющий parser с явным
  allowlist sheets/fields; полный workbook dump запрещён.
- Файлы из локальных и сетевых upstream-путей вне репозитория считать
  read-only источниками.
- Не выводить в логи и отчеты email, телефоны, адреса, содержимое документов,
  токены, cookie и полные исходные строки клиентов.
- Любой доступ пользователя к ребенку, документу, договору или обращению
  проверять на сервере по владельцу; скрытого поля формы недостаточно.
- Административные изменения и чтение чувствительных документов должны
  попадать в audit log.

## Изменения поведения

- Требование изменяется в его каноническом документе, а критерий проверки — в
  `docs/spec/ACCEPTANCE_CRITERIA.md` и при необходимости в тест-плане.
- Не дублировать полное бизнес-правило в roadmap или промпте: использовать
  ссылку и идентификатор требования.
- Любое изменение D1-модели оформлять новой миграцией; примененные миграции не
  переписывать.
- Импорт и повторные действия пользователя проектировать идемпотентно.

## Проверки

Перед завершением реализации выполнять:

```bash
npm run check
npm test
npm run build
```

Если какая-либо проверка неприменима или не проходит по внешней причине, это
нужно явно указать в результате. Deploy и операции с production выполняются
только по отдельному прямому поручению.
