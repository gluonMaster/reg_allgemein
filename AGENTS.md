# Правила работы с репозиторием

## Перед изменениями

1. Прочитать `docs/README.md` и `docs/spec/MVP_SPEC.md`.
2. Открыть тематический документ, который является источником истины для
   изменяемого поведения.
3. Проверить `docs/spec/OPEN_QUESTIONS.md`: нерешенный вопрос нельзя молча
   превращать в бизнес-правило.
4. При работе по roadmap прочитать раздел соответствующего этапа, persistent
   handoff предыдущего этапа и обновлять
   `docs/implementation/handoffs/stage-NN.md`.

Границы этапов заданы в `docs/implementation/ROADMAP.md`. В локальной рабочей
копии могут находиться игнорируемые Git операционные промпты, но они
необязательны для реализации, не являются источником истины и не должны
подменять спецификацию, тематические документы или roadmap.

Портал регистрации — самостоятельное приложение со своим deployment,
origin и runtime-ресурсами. Официальный сайт `kolibri-dresden.de` — внешняя
отдельная система; его интеграция с порталом ограничена обычными HTTPS-
ссылками. Не изменять CMS, код, базу, файлы, deployment или ссылки
официального сайта без отдельного прямого поручения.

## Данные и безопасность

- Не коммитить `.accdb`, `.mdb`, клиентские `.xlsm`, исходные Office-шаблоны и
  выгрузки с PII/служебными metadata, секреты и сгенерированные import
  artifacts. В Git допускаются только обезличенные профили и manifest/README
  источников.
- Не открывать клиентские Office-файлы через Excel/COM/LibreOffice и не
  исполнять embedded VBA/macros. Разрешён только неисполняющий parser с явным
  allowlist sheets/fields; полный workbook dump запрещён.
- Файлы из локальных и сетевых upstream-путей вне репозитория считать
  read-only источниками.
- Не выводить в логи и отчеты email, телефоны, адреса, содержимое документов,
  токены, cookie и полные исходные строки клиентов.
- Любой доступ пользователя к ребенку, документу, договору или обращению
  проверять на сервере по владельцу; скрытого поля формы недостаточно.
- Административные изменения и чтение чувствительных документов должны
  попадать в audit log.

## Изменения поведения

- Требование изменяется в его каноническом документе, а критерий проверки — в
  `docs/spec/ACCEPTANCE_CRITERIA.md` и при необходимости в тест-плане.
- Не дублировать полное бизнес-правило в roadmap или промпте: использовать
  ссылку и идентификатор требования.
- Любое изменение D1-модели оформлять новой миграцией; примененные миграции не
  переписывать.
- Импорт и повторные действия пользователя проектировать идемпотентно.

## Приоритет результата

Ближайший явно названный владельцем пользовательский milestone имеет приоритет
над гипотетическим совершенством кода. По поручению 2026-09-16 ближайший
milestone — ограниченный production `trial-intake` по `SYS-05`,
`docs/domain/TRIAL_INTAKE.md` и `docs/implementation/TRIAL_INTAKE_RELEASE_TZ.md`.
Полный Access-protected preview по `SYS-04`/`OQ-036` сохраняется как последующая
работа и не подменяет срочный scope. Обязательные контуры выбранного milestone
нельзя заменять stub, fake provider, `feature_disabled` или одним локальным тестом.

Перед исправлением или новым review-loop каждую находку нужно связать с
ближайшим milestone и классифицировать:

- `P0` — риск утечки/потери данных, обхода authorization, необратимой remote
  ошибки, неверного target или отсутствия rollback. Немедленно блокирует работу;
- `P1` — реально ломает обязательный пользовательский или operator flow текущего
  milestone. Исправляется до продвижения;
- `P2` — ограниченная robustness/maintainability проблема без доказанного отказа
  текущего flow. Записывается в backlog и не открывает новый цикл сама по себе;
- `P3` — косметика, вкусовая полировка или гипотетический edge case без
  правдоподобного воздействия. Не блокирует milestone.

Если `P0/P1` нет, агент не должен задерживать следующий deploy/manual gate ради
`P2/P3`. Связанные мелкие правки объединяются в один пакет и получают один
focused regression run. Новый рефакторинг во время deploy начинается только
если без него нельзя пройти обязательный flow безопасно.

Deployment выполняется короткими квазиатомарными фазами. У каждой фазы заранее
фиксируются exact target, ожидаемый пользовательский результат, минимальная
проверка и rollback/containment. Зелёная фаза не переоткрывается без фактического
drift, нового material diff или воспроизводимого `P0/P1`.

### Обязательный checkpoint после remote mutation

Remote mutation — это D1/R2 write, migration/import transition, Worker deploy/
rollback/traffic change, Access/flag/var/secret change, provider send либо
bootstrap/role/session change. После **каждой попытки** такой атомарной операции,
включая failed или ambiguous результат, и до следующей remote mutation агент
обязан:

1. read-only проверкой сверить фактическое postcondition в целевой среде;
   одного exit code или текста команды недостаточно;
2. обновить `docs/implementation/STAGE_13_ACTIVE_STATE.md`: UTC, текущую фазу,
   разрешённый scope, sanitized target fingerprint, candidate/version,
   факты before/after, `success|failed|ambiguous`, evidence, rollback/containment
   и ровно одно следующее атомарное действие;
3. не записывать в tracked state secrets, PII и полные resource IDs: они остаются
   только в защищённом Git-ignored evidence;
4. при failed/ambiguous результате не продвигать фазу и не повторять write
   вслепую; сначала зафиксировать containment или hard blocker;
5. сохранить обновлённый active state отдельным небольшим docs-only commit до
   следующей remote mutation. Handoff обновляется на границе фазы/сессии, а
   readiness checklist — только если изменился фактический gate.

Для такого status-only commit выполняются только `docs:check`, `release:scan` и
`git diff --check`; полный runtime suite не повторяется.

После каждой атомарной операции агент также сообщает владельцу
`rollover_required: yes|no`, `recommended_next_session_mode: Medium|High|Max` и
простую причину выбора. Режим выбирается по фактической ситуации:

- `Medium` — следующая работа только read-only/docs/evidence/manual inspection,
  без unresolved ambiguity и без remote write;
- `High` — обычный режим планового deploy: target, процедура, postcondition и
  rollback/containment известны; это default для следующей deploy-сессии;
- `Max` — только при подтверждённом серьёзном риске: возможно затронута неверная
  среда/production; итог потенциально необратимой записи неоднозначен; recovery
  или rollback отсутствует/не сработал; обнаружены data/schema corruption,
  Access/authorization bypass, secret exposure либо несовместимость deployed
  code и schema. Нужно простыми словами назвать, что может быть повреждено,
  какое evidence это показывает, почему `High` недостаточно и какое решение
  должна безопасно принять следующая сессия.

Обычный provider rejection, подтверждённый no-write timeout, косметический/UI
дефект, уже локализованная docs-ошибка или штатная fail-closed остановка сами по
себе не являются основанием для `Max`. Рекомендация режима не расширяет
разрешения и не требует rollover, если текущая сессия безопасно сохраняет точный
context.

### Группировка checkpoint-коммитов перед push

Пошаговые status-only commits нужны для восстановления во время работы, но
публиковать их по одному не требуется: в истории они растворяют смысловые
изменения кода. К сентябрю 2026 из 371 коммита 303 трогали только `docs/`,
одна серия подряд достигала 95 коммитов, а кода касались 68.

Перед `git push` подряд идущие docs-only checkpoint-коммиты завершённой фазы
объединяются в один. Правила:

- объединять только ещё не отправленные коммиты. Опубликованная история не
  переписывается, force-push запрещён;
- объединять только сплошную серию, где каждый коммит трогает исключительно
  `docs/`. Коммит с кодом серию прерывает и остаётся отдельным;
- дерево результата обязано совпадать с деревом последнего коммита серии:
  `git diff <старый HEAD> <новый HEAD>` пуст;
- темы объединённых коммитов сохраняются в теле результирующего, чтобы
  пошаговая хронология не пропала;
- до объединения проверить, что ни один tracked документ не ссылается на хеш
  исчезающего коммита. Документы этапа цитируют настоящие хеши, а
  `scripts/check-stage13-continuity.ts` проверяет существование
  `reviewed_candidate`. Ссылку либо обновить, либо оставить этот коммит отдельным;
- после объединения выполнить `npm run docs:check`.

Тему status-only commit начинать с `docs(checkpoint):`, чтобы фильтрация
работала и по теме, и по путям.

Смысловую историю читать с фильтром по путям, а не по словам в теме:

```bash
git log -- . ':(exclude)docs'
```

Удобный алиас (настраивается один раз на машине, в Git не хранится):

```bash
git config --local alias.code-log "log --pretty=format:'%h %ad %s' --date=short -- . :(exclude)docs"
```

## Проверки

Проверки выбираются пропорционально фактическому риску и изменённой поверхности.
Перед запуском агент кратко фиксирует, какие production paths затронуты, какие
tests их покрывают и почему выбранный набор достаточен. Нельзя автоматически
запускать полный suite после каждого небольшого изменения.

- Для изменения бизнес-логики запускать exact unit/integration suites
  изменённых модулей и их непосредственных consumers.
- Для docs/prompt/agent-instruction/test-only изменений запускать только
  релевантные docs/checker/unit tests. Если изменён исполняемый TypeScript
  checker, дополнительно выполнять `npm run check`; `npm run build` нужен, когда
  изменение может затронуть сборку либо когда это быстрый candidate sanity gate.
- Для UI/route/runtime изменения добавлять affected browser/E2E scenarios, но
  не весь E2E suite, если impact надёжно ограничен.
- Полный `npm test` и полный E2E обязательны перед release/deploy после
  материального runtime, shared-infrastructure, migration, dependency/toolchain
  или cross-cutting изменения; при невозможности надёжно ограничить impact; либо
  по прямому поручению владельца/reviewer.
- Если exact ancestor уже прошёл полный suite, а новый diff ограничен
  docs/checker/tests и не меняет runtime, migrations, dependencies или config,
  полный suite не повторять. В handoff указать reused exact SHA/evidence и
  фактически выполненные focused checks.
- Независимый review применяет ту же risk-proportional матрицу. Новый reviewer
  не должен повторять сотни unrelated tests только ради docs-only или локального
  validator diff.

Типовая полная release-цепочка, когда она действительно применима:

```bash
npm run check
npm test
npm run build
```

В результате явно перечислять выполненные и осознанно не запущенные проверки с
обоснованием. Assertion failure релевантного test нельзя списывать на
неприменимость. Deploy и операции с production выполняются только по отдельному
прямому поручению.
