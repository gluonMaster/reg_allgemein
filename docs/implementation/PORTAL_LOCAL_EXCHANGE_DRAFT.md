# Обмен между порталом и локальной картотекой

Дата: 2026-09-14. Черновик для обсуждения. Код, базы и действующее ТЗ не меняются.

Цель первой версии: админ выбирает нужные изменения портала, скачивает понятный
файл и переносит сведения локально. Один-два раза в месяц либо чаще он загружает
в портал актуальные утверждённые данные локальной базы.

## Уже решено

- FamilyID сохраняет полную форму: локальные семьи — `1. XXXX`, новые семьи
  портала — `2. XXXX`. Одинаковые цифры при разных префиксах не означают одну
  семью. Общая нумерация и резервирование не нужны.
- Экспортируются только подтверждённые админом изменения, значимые для `Kartei`.
  Регистрация аккаунта, пробные заявки, переписка и промежуточные документы
  сами по себе не экспортируются.
- Стоимость и начисления подготавливаются локальным админом штатными средствами.
  Портал передаёт утверждённую базовую цену и даты, не месячные начисления.
- Проверка Суперадмина остаётся локальной:
  `pre_tblKartei → утверждение → tblKartei`; при отклонении —
  `decl_tblKartei → исправление в Admin → повторное утверждение`.
  Портал получает окончательные данные основной таблицы; причины отклонения
  и локальные промежуточные версии туда не возвращаются.

## Предлагаемый экспорт из портала

1. В админском интерфейсе открыть «Обмен с локальной базой → Экспорт».
2. Выбрать период и одну или несколько категорий: новая семья/ребёнок/занятие;
   смена группы или пакета; смена типа договора; изменение базовой цены;
   прекращение; пауза/возобновление; исправление личных данных.
3. Увидеть таблицу: FamilyID, ребёнок, занятие, суть изменения, прежнее и новое
   значение, дата подтверждения, дата действия, отметка о предыдущих экспортах.
   Раскрытие строки показывает необходимые для переноса сведения.
4. Поставить галочки у нужных записей. Доступны «Выбрать все по фильтру» и фильтр
   «Ещё не экспортировались / Уже экспортировались / Все».
5. Скачать файл выбранных записей. Система сохраняет состав выгрузки.

Одна запись — конкретное подтверждённое изменение с необходимыми сведениями
о семье и ребёнке. Оформленный и затем прекращённый между выгрузками договор
не должен исчезнуть из списка событий.

Предлагаемый файл — **XLSX без макросов** для чтения и копирования: ID и версия
изменения, категория, полный FamilyID, ребёнок/занятие, нужные личные данные,
тип договора, базовая цена, даты и основание; локальный ID, если известен.
Номера и телефоны сохраняются текстом, клиентский текст — без исполнения формул.
Это не готовый лист `Kartei` для массовой вставки. Выгрузка доступна только
админу, скачивание аудируется.

## Учёт выгрузок и локальная работа

Предлагается небольшой журнал в базе портала: номер выгрузки, дата, админ,
перечень ID и версий включённых изменений. Для него потребуется новая миграция.
Новая подтверждённая версия ранее выгруженного изменения видна как новая.
Перед созданием файла повторно проверяются выбранные версии событий.

Отметка означает **«включено в выгрузку»**, но не доказывает скачивание, ввод
в `Kartei` или утверждение. После сбоя можно повторно получить тот же файл.
Повторная выгрузка разрешена и явно видна.

Для срочного запуска предлагается **ручной перенос из файла** через привычные
формы Admin. Они обеспечивают `Zahlung`, ID строк, пометки, расчёты и историю.
Простой безопасный автоматический импорт пока не подтверждён. Последующее
улучшение — заполнение существующей формы из выбранной записи файла,
с просмотром результата админом.

## Предлагаемый импорт локальных данных в портал

1. Локальный помощник «Подготовить данные для портала» получает выбранные
   источники и период, использует существующие парсеры и создаёт файл только
   с разрешёнными полями. Исходники не меняются, макросы не запускаются.
2. В админском разделе «Импорт» выбрать подготовленный файл.
3. До применения увидеть результат проверки: сколько семей, детей и занятий
   прочитано; что добавится, изменится или исчезло из источника; какие ошибки
   и неоднозначные связи требуют решения.
4. Подтвердить применение. После него увидеть фактический результат и номер
   импорта. Неопределённый результат после обрыва сначала проверяется по этому
   номеру; повторная загрузка не создаёт дубли.

Клиентские сведения берутся из основной `tblKartei`, без pending/declined.
Прайс, PlusBText и опубликованное расписание — отдельные обновляемые источники;
состав первого импорта уточняется ниже. Начисления остаются локально.

Импорт сохраняет аккаунты, владельцев, документы и необработанные онлайн-изменения.
Неоднозначные связи решает админ; совпадение имени не создаёт связь автоматически.
Пропавшая строка не означает удаление клиента или расторжение договора.
Ошибка проверки сохраняет рабочую версию; восстановление после ошибочного
импорта не должно стирать последующие действия пользователей.

## Что уже есть и чего недостаёт

Есть парсеры Access, PlusBText, прайса и расписания, версии импортов и диагностика.
Веб-раздел импорта сейчас показывает журнал, но не запускает загрузку файлов.
Нужно завершить удалённое применение: действующая production-процедура пока
блокирует публикацию. Новая кнопка не заменяет её защитные проверки.

Есть подтверждение админом нового договора и финального изменения цены.
Отдельных готовых процессов перевода, смены типа действующего договора и паузы
нет. Их включение в список категорий само по себе не создаст события экспорта.

Access-импортёр сейчас принимает только FamilyID `1. …`. Возврат локальных записей
семей `2. …` и связь вручную созданных занятий с порталом требуют доработки.
Даты прекращения и паузы нужно брать из явных данных, не угадывать по начислениям.

## Вопросы до реализации

1. **Файл и ручной ввод.** Подходит XLSX для копирования данных в существующие
   формы Admin? Альтернатива — HTML-карточки для просмотра и печати. Рекомендация:
   XLSX и ручной ввод в первой версии, без изменения локальных книг.
2. **Период выгрузки.** Рекомендую отбор по дате подтверждения админом, включая
   границы выбранных дней по времени Берлина; дату действия показывать отдельно.
   Нужен ли также отбор по дате начала действия изменения?
3. **Недостающие категории.** Для пауз, переводов и смены типа договора достаточно
   пока отдельной записи, которую админ оформляет и подтверждает для экспорта,
   либо сначала обязательны полноценные клиентские процессы? Рекомендация:
   отдельная запись для локального учёта; сама она не меняет подписанный договор.
4. **FamilyID локально.** Сохраняем при ручном вводе `2. XXXX` в колонке A,
   включая `Zahlung`? Это рекомендуемый вариант, но совместимость локальных
   процедур ещё надо проверить. Если локально обязателен новый `1. XXXX`,
   потребуется явная связь двух полных номеров.
5. **Связь занятий после ручного ввода.** Допустимо при следующем импорте один раз
   выбрать в портале локальную строку для соответствующего онлайн-занятия?
   Рекомендую это вместо новых служебных полей в Admin. Выгрузка сама по себе
   не подтверждает перенос; точное совпадение данных тоже не доказывает принятие.
6. **Первый обратный импорт.** Какие рабочие годы и источники нужны сразу:
   Access + PlusBText, также прайс и расписание? Где находятся актуальные файлы
   и опубликованное расписание? Подходит предложенный локальный помощник
   подготовки файла, или нужен выбор исходных файлов прямо на странице портала?
7. **Исправленные условия.** Если утверждённая локальная цена, группа или срок
   отличаются от оформленного онлайн-договора, предлагаю показать админу
   расхождение для отдельного решения, сохранив документ. Подходит ли это?

Минимальная проверка реализации: доступ только админу; фильтры и галочки;
сохранение ID/дат/текста; повторное скачивание и новая версия события;
повторный импорт и возврат семьи `2. …` без дублей; конфликт, повреждённый файл
и обрыв обмена. Эти проверки ещё предстоят.
