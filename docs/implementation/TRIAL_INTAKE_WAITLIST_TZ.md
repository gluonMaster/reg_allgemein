# Лист ожидания для плановых курсов — план реализации и выпуска

Дата: 2026-11-05, обновлено 2026-11-09. Статус: **ТЗ подготовлено по решениям
владельца OQ-049, OQ-050 и OQ-052 (тексты утверждены) и OQ-051 (сущность курса и
перепривязка); реализация идёт, выполнены этапы 01–05, идёт выпуск портала 06**.

Требования — [TRIAL_INTAKE_WAITLIST](../domain/TRIAL_INTAKE_WAITLIST.md) (WL-01–15),
приёмка — [WL-AC](../spec/ACCEPTANCE_CRITERIA.md#лист-ожидания-wl-ac). Документ не
дублирует правила, а задаёт этапы, точки изменений, проверки и фазы выпуска. Это
расширение production `trial-intake` по поручению владельца 2026-11-05; для
классификации находок P0–P3 по AGENTS.md ближайший milestone — выпуск листа
ожидания в этом объёме. Deployment и запись на сервер редактора расписания — только
по отдельному прямому поручению.

## Решение

Плановая карточка расписания → `/warteliste` с ценой и выбором тарифа →
обязательное согласие → проверка email → подтверждающее письмо и Telegram →
статус очереди у администратора → старт курса администратором с пробной отправкой
себе → письмо о старте с PDF каждой семье → договор в офисе.

Портал узнаёт плановое занятие по названию группы, поэтому формат каталога TIN-06
не меняется, и единственный порядок выпуска — сначала портал, затем экспортер:
старые CTA плановых карточек ведут на `/probestunde`, и обновлённый портал сразу
перенаправляет их в лист ожидания.

## Что проверено в исходниках

Исследование 2026-11-05 по рабочему дереву поверх последнего коммита с кодом
`beed372`; remote control plane и production D1 не читались, живое расписание —
публичным GET.

Remote conformance PR-F07 не пройдена | Адаптер и шрифт импортируются без изменения файлов полного портала; пробная отправка в фазе 06 — первая remote conformance |

## Минимальная модель

Одна новая append-only миграция `0032_trial_intake_waitlist.sql` создаётся на
этапе 01 для всей функции. Ниже — эскиз; точный SQL согласуется с
[DATA_MODEL](../architecture/DATA_MODEL.md) на этапе 01.

- `trial_intake_requests.kind` — `trial|waitlist`, default `trial`, добавляется
  `ALTER TABLE` как `kind` в `0029`. Контакты, дети, verification, receipt,
  idempotency и retention запроса переиспользуются.
- `trial_intake_planned_prices` — ключ сущности (PK), поля сущности и последний
  кабинет для показа и сравнения, `monthly_cents`, `yearly_cents`, `min_participants`
  (default 3), причины оранжевой метки (NULL — метки нет), кто и когда изменил.
- `trial_intake_waitlist_entries` — 1:1 с запросом листа (`ON DELETE CASCADE`):
  ключ сущности, снимок занятия, `tariff`, обе суммы и порог на момент записи,
  версия текста согласия, статус `waiting|started|withdrawn|cancelled|expired`,
  ссылка на старт, nonce и UNIQUE hash токена выхода, время изменения статуса.
  Дети записи — `trial_intake_children` того же запроса; `trial_intake_items` у
  записи листа не создаются, поэтому список заявок на пробное её не видит.
- `trial_intake_waitlist_starts` — ключ сущности, дата первого занятия, снимок
  занятия из каталога, число участников, кто и когда, `reopened_at`; один незакрытый
  старт на сущность (частичный UNIQUE при `reopened_at IS NULL`).
- `trial_intake_waitlist_rebinds` — append-only журнал: откуда и куда (ключи и снимки
  карточек), вид (`plain|notify|price`), отличия и причины, суммы до и после, кто и когда.
- `trial_intake_waitlist_price_confirmations` — запись, строка журнала со сменой
  продолжительности, решение (`confirmed|declined`), новая сумма по тарифу записи,
  администратор и время. Красная метка вычисляется: есть подтверждённая ожидающая
  запись, созданная до последней такой перепривязки, без отметки по ней. «Последняя
  такая» — последняя строка вида `price` в цепочке журнала, которая привела очередь
  к её текущему ключу: строка «→ ключ», затем строка «→ её откуда» раньше неё и так
  далее; поэтому метка переходит с очередью и через последующую обычную
  перепривязку. Сервер вычисляет эту строку и передаёт её ID в условие SQL старта.
- `trial_intake_waitlist_email_outbox` — письма о старте и пробные: запрос, старт
  либо выбранная дата пробы, admin-получатель пробы, обычные поля lease/retry
  как у `trial_intake_email_outbox`, sha256 отправленного PDF.
- `trial_intake_waitlist_documents` — PDF (BLOB до 1 MiB), sha256, размер,
  renderer и время; `ON DELETE CASCADE` с запросом; только документы писем о
  старте, пробные PDF не хранятся.
  Расход Browser Run для дневного лимита учитывается без PII.

Обязательные триггеры WL-06 — отдельные `RAISE(ABORT)` с понятными сообщениями:

1. снимок записи (занятие, тариф, суммы, порог, согласие, hash выхода) не
   изменяется после вставки;
2. вставка записи требует строку цены той же сущности с теми же суммами;
3. вставка ожидающей записи невозможна, если у сущности есть незакрытый старт;
4. изменение `monthly_cents`/`yearly_cents` отклоняется, пока у сущности есть запись
   в статусе `waiting`;
5. удаление цены отклоняется при том же условии;
6. смена ключа сущности в записи требует строки журнала с теми же «откуда» и «куда»;
7. строка журнала без смены продолжительности требует равных сумм «откуда» и «куда»,
   а строка вида `price` — действительно разной продолжительности.

Перепривязка выполняется одной D1 batch: цена цели, строка журнала, отмена
неподтверждённых, смена ключа ожидающих записей, удаление прежней строки цены, audit.
Запрет смены предмета проверяет сервер: чистая функция сравнения покрыта unit-тестами.

Миграция аддитивна: новая колонка имеет default, новые триггеры висят только на
новых таблицах. Текущий Worker совместим с ней, откат Worker не требует отката
схемы. `foundation-d1` и upgrade-тест последовательности миграций дополняются
`0032`.

## Изоляция и точки изменений

Всё новое — в `src/lib/trial-intake/` по TIN-11. Ориентир раскладки, точные имена
выбирает реализация:

- `planned.ts` — правило WL-01, ключ сущности и сравнение двух карточек для WL-15
  (browser-safe, как `closed.ts`);
- `server/waitlist*.server.ts` — запись, подтверждение, выход, старт, перепривязка,
  статусы, cleanup, шаблоны писем и Telegram;
- `server/prices*.server.ts` — цены, блокировки, CSV/XLSX;
- `server/waitlist-pdf.server.ts` — HTML документа, рендер, хранение, resolver;
- компоненты формы листа, выхода, админ-страницы, диалога старта; маршруты
  `src/routes/warteliste/**`, `src/routes/admin/trial-intake/warteliste/**` и
  PDF записи — тонкие обёртки.

Точки подключения: allowlist режима, intake email store (claim и mark для новой
таблицы), attachment resolver worker в intake mode, cleanup, outbox context для
карточки доставки («Warteliste» вместо «Probestunde»), admin-навигация, i18n.
`src/lib/server/contracts/*` не меняется: адаптер Browser Run и шрифт DejaVu
импортируются как есть. Если без правки файла полного портала не обойтись, это
меняет набор проверок деплоя на полный `npm test` (AGENTS.md) — сообщить.

Для XLSX предпочтителен `fflate` (уже проверен в lockfile, MIT) с переводом в
runtime dependencies и записью в [DEPENDENCY_POLICY](../operations/DEPENDENCY_POLICY.md);
допустима реализация на встроенных `CompressionStream`/`DecompressionStream`.
`xlsx`/SheetJS не возвращать. Парсер евро в центы — собственный строковый, по
образцу import-модулей; форматирование — `formatEuro` из `$lib/i18n/locale.ts`.

## Публикация короткими фазами

Checkpoint после каждой попытки remote mutation — по AGENTS.md, отдельной записью
`TIN11-…` в [active state](STAGE_13_ACTIVE_STATE.md) и docs-only commit. Запись на
сервер редактора и публикация HTML на Netlify — тоже отдельные шаги с checkpoint.

| Фаза | Target и результат | Минимальная проверка | Откат / containment |
| --- | --- | --- | --- |
| 06.1 Preflight | Активная версия, pending только `0032`, счётчики D1, оба Cron | read-only сверка, drift нет | — |
| 06.2 Схема | `0032` в production D1 | список миграций, таблицы и триггеры, `foreign_key_check` до и после | миграция аддитивна; прежний Worker совместим |
| 06.3 Worker | candidate с binding `BROWSER` и прежними vars и secrets | версия на 100 %, Cron, имена secrets, новые маршруты отвечают, плановая ссылка `/probestunde` перенаправляет | `wrangler rollback` на версию из preflight; закрыть плановые курсы в админке или `TRIAL_INTAKE_ACCEPTING=false` |
| 06.4 Цены | Владелец вводит цены трёх курсов в админке | статусы «sammelt: 0 von 3», audit | удалить цену (не заблокирована) |
| 06.5 Живой flow | Контрольная запись владельца на свой адрес → письма 1–2 → Telegram; цена заблокирована | inbox, Telegram, D1 aggregate, блокировка в UI | выход по ссылке |
| 06.6 PDF | Пробное письмо о старте себе по контрольной записи | PDF открывается, умлауты, €, кириллица, одна страница; outbox `sent` | при отказе Browser Run — стоп и решение владельца; старт курса не выполнять |
| 06.7 Выход | Владелец выходит по ссылке | запись «вышла», счёт 0, блокировка снята | — |
| 07.1 Код редактора | Изменённые файлы визуализатора на сервер по процедуре редактора | хеши до и после, резервная копия `before/` | вернуть файлы из `before/` |
| 07.2 Публикация | Штатная публикация, затем загрузка HTML на Netlify владельцем | плановые карточки с новой CTA и подписью без суффикса; множество ID каталога совпадает с прежним; прочие CTA без изменений | вернуть предыдущий deploy Netlify |

Не группировать несколько writes под один поздний checkpoint. Контрольный flow
выполняется один раз на согласованный адрес; негативные сценарии локальных тестов
на production не повторяются. Перепривязка проверяется локально: на production она
потребовала бы менять настоящее расписание. Реальный старт курса — обычная работа
бюро после выпуска, а не шаг приёмки.

## Не делать / отложено

- Автоматический старт курса (OQ-049); отмена или перенос уже выполненного старта;
  письма об отмене планового курса.
- Автоматическая перепривязка без решения администратора и объединение двух очередей.
- Письма семьям и Telegram о перепривязке: семьи обзванивает бюро (OQ-051). Смена
  тарифа при обзвоне: семья выходит и записывается заново.
- Публичный счётчик записанных; Telegram о выходе и старте; письмо бюро о сбое
  письма о старте — статус виден в админке.
- Оплата, банковские реквизиты, SEPA, генерация полного договора; цены обычных
  курсов, скидки и суммы по семье; цены в HTML расписания.
- Смешанная заявка «пробное + лист» и несколько курсов в одной записи листа.
- Изменение модулей полного портала, pricing/contracts и официального сайта.

## Риски и допущения

- **Browser Run в production не проверялся** (PR-F07). Фаза 06.6 — первая remote
  conformance. Если binding или quota недоступны, другой конвертер не подключается
  молча (ADR-014, DEPENDENCY_POLICY): запись в лист работает, старт ждёт решения.
- **Вложения Resend в production не использовались** — покрывает та же фаза.
- **Правило плейсхолдера.** Иная формулировка группы не делает курс плановым;
  админ-страница показывает, что распознано.
- **Смена ключа сущности.** Любая правка дня, времени, предмета, преподавателя,
  здания или возраста плановой карточки с очередью требует решения администратора;
  пока его нет, запись на новую карточку закрыта отсутствием цены. Правило возраста в
  коде тоже входит в ключ: его изменение покажет такие курсы как исчезнувшие.
- **Формулировки обещания** твёрдые, но юридической обязательности онлайн-записи
  не заявляют; утверждены владельцем (OQ-050).
- **Cache каталога** 5 минут: изменение расписания портал видит с этой задержкой.

## Калибровка сложности

Объём следует из поручения и решений OQ-049/OQ-050/OQ-051: цены без хардкода с
CSV/XLSX, контур цены, статусы, класс Telegram, три письма, PDF и старт
администратором с предпросмотром письма и PDF — его даёт пробная отправка себе, она
же единственная проверка реального пути PDF и вложения до первого старта; сущность
курса, инструмент перепривязки, оранжевый статус с ручным снятием и обзвон при смене
продолжительности. Формат каталога, Telegram-триггеры, таблица писем TIN и модули
полного портала не меняются; проверка email, праздники, outbox, recovery и retention
переиспользуются.

Сверх прямых требований оставлено: отказ при двух одинаковых сущностях как страховка
(иначе неясно, о каком времени писать семьям); отмена неподтверждённых записей при
перепривязке (их проверочное письмо описывает прежний курс); «Als neuen Kurs öffnen»
(ключ сущности без номера группы иначе навсегда закрыл бы, например, новый первый
класс в то же время через год); вывод семьи администратором по звонку (иначе
ушедшая семья держит цену и счёт); предпросмотр импорта (опечатка в цене видна до
того, как первая запись её заблокирует); хранение отправленного PDF (повтор письма
шлёт тот же файл, бюро открывает документ семьи в офисе); подпись плановой
карточки без технического суффикса (эта карточка и так меняется).

Не входит в объём: синхронизация зеркала экспортера и roundtrip в портале, изменение
PDF-версии расписания, повторная сверка сервера редактора в этапе экспортера (её
делает выкладка перед записью), хранение пробных PDF, тест конфигурации без изменения
конфигурации и публичный счётчик.
