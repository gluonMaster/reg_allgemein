# ТЗ: быстрое улучшение интерфейса preview-портала

Дата: 2026-09-15. Основание: браузерный аудит и уточнение владельца от этой даты.
Статус: подготовлено для реализации; в сессии подготовки изменён только этот документ.
Калибровка объёма: 2026-09-15, по исходной переписке и skill `spec-rightsize`.

## 1. Результат и границы

Получить аккуратный, понятный интерфейс на уже загруженных синтетических данных,
в котором владелец сможет самостоятельно проверить заявки и договоры и провести
демонстрацию. Приоритет — навигация, доступ к существующим функциям, размеры форм
и понятные состояния. Не превращать пакет в переработку приложения.

В пакет входят общая оболочка public/parent/admin, кабинет, каталог, оформление
существующих форм и списков, диагностика 403 и исправление подтверждённых ошибок
на затронутых страницах. Заявки и договоры проверяются агентом локально в пределах
изменённого UI; реальные preview-сценарии с отправкой и оформлением выполняет владелец.

Ограничения владельца:

- **Telegram не исследовать, не изменять и не тестировать внешними вызовами без
  отдельного прямого указания.** Не выполнять send/retry/reconciliation, не менять
  outbox, расписание доставки, конфигурацию или связанные operational gates.
  Общие CSS и навигация могут наследоваться существующей страницей outbox;
  её специальные формы, тексты и поведение не входят в пакет.
- Не отправлять в preview заявки, обращения и уведомления, не создавать,
  не принимать и не активировать договоры для проверки этого UI-пакета.
  Не запускать lifecycle uploads, PDF/R2/email или демонстрационный seed.
- Новый мастер создания договора, автоматическое заключение договора,
  новые типы заявок, импорт/экспорт и обмен с локальной картотекой отложены.
- Существующие данные, владельцы объектов, цены, названия групп, PDF и договорные
  доказательства сохраняются. Нельзя подменять отсутствующие данные красивыми
  вымышленными суммами, показателями или статусами.
- Deployment в preview требует отдельного прямого поручения. Production и
  официальный сайт находятся вне scope. Подготовка ТЗ не разрешает deploy.

Источники требований: [MVP_SPEC](../spec/MVP_SPEC.md) (`SYS-01–04`, `AUTH-05–09`,
`CAB-01–05`, `CHILD-01–03`, `CAT-01–04`, `CONTRACT-01`, `UI-01`, `TIME-01`),
[WORKFLOWS](../domain/WORKFLOWS.md), [CONTRACTS](../domain/CONTRACTS.md),
[ACCEPTANCE_CRITERIA](../spec/ACCEPTANCE_CRITERIA.md) и
[TEST_PLAN](TEST_PLAN.md). В [OPEN_QUESTIONS](../spec/OPEN_QUESTIONS.md) на дату
чтения открытых вопросов нет. Этот документ задаёт пакет работ, а не заменяет
канонические бизнес-правила. Новые UI-критерии и дополнение входа из каталога
нужно внести в канонические документы при реализации.

## 2. Основание: что обнаружено

Аудит 2026-09-15 использовал браузерный Playwright через подключение к Chrome,
DOM-измерения и скриншоты. Обычный viewport — 1536 px, мобильный — 390 px.
Изолированные MCP Playwright/Chrome DevTools открывали пустые браузеры и не видели
вкладки владельца; поэтому для существующих сессий использован браузерный
Computer Use. Авторизованные формы не отправлялись.

Числа — измерения конкретного состояния, не обязательные константы будущего UI.
Новый P1 фиксируется только после воспроизведения отказа текущего обязательного
flow. Отсутствие такого отказа не мешает выполнить явно заказанный визуальный
пакет P2. Прочие P2/P3 не расширяют его и не открывают новый review-loop.

Быстрый вход к договору сохраняется: владелец прямо указал отсутствие этого пути.
Постоянная боковая панель, отдельная диагностическая система и полная переработка
каждой административной формы не являются самостоятельно согласованными результатами.
Способ компоновки и небольшие общие компоненты выбирает исполнитель.

## 3. PVUI-01: выяснить 403 и исправить объяснение доступа

### Установлено по коду и предыдущему наблюдению

- [hooks.server.ts](../../src/hooks.server.ts) возвращает **401**, если защищённый
  маршрут не получил authenticated user; **403** — при несовпадении роли.
  В обоих случаях ошибочно используется текст `auth.invalidCredentials`.
- [session.ts](../../src/lib/server/auth/session.ts) использует одну host-only
  cookie `kolibri_session` с `Path=/` для обеих ролей. Успешный
  [login](../../src/routes/auth/login/+page.server.ts) записывает её заново.
  Вкладки и обычные окна одного профиля Chrome используют общее хранилище cookie.
- Истёкшая/отозванная сессия и несовпадение session version дают отсутствие user,
  то есть ожидаемый 401. Проверка Origin формы не блокирует обычный GET.
- В аудите старая вкладка сначала показывала родительский кабинет, затем переход
  на пробное и повторное открытие кабинета дали 403; админские страницы работали.

Наиболее обоснованное объяснение: вход администратора заменил используемую
вкладками cookie, а первоначальный кабинет оставался старым отображённым документом.
Это не доказательство повреждения или удаления родительской сессии в D1.
Содержимое cookie и актуальная запись этой сессии отдельно не исследовались.

### Работа

1. На существующих локальных auth fixtures воспроизвести два входа в разных вкладках
   **одного browser context**:
   parent → admin → переход/обновление parent-страницы. Зафиксировать роль и
   HTTP-статус без токенов и контактов.
2. Сравнить с двумя изолированными contexts: parent открывает кабинет и форму
   пробного с 200; admin открывает свой раздел с 200, parent-маршрут — с 403.
   Переиспользовать соответствующие сценарии `authenticated-access.spec.ts`,
   дополняя их только отсутствующим случаем или проверкой новых текстов.
3. Для отсутствующей сессии проверить новый ответ 401. Проверки истечения и отзыва
   брать из существующего auth-покрытия по фактическому diff; не строить для них
   новый browser lifecycle, если механизм сессий не изменился.
   Если действующий parent в отдельном context получает 403, исследовать
   middleware/route policy и исправлять подтверждённый P1 до завершения пакета.
4. Разделить тексты: 401 — «Для продолжения войдите в учётную запись»;
   403 — «Эта страница недоступна для текущей роли». Для известного admin на
   parent-маршруте пояснить, что нужен вход родителя, и дать переход в админку.
   Ошибку неправильных credentials сохранить для фактически неуспешного входа.
5. Согласовать оформление и текст прямого HTML-ответа из
   [error-response.ts](../../src/lib/server/i18n/error-response.ts) и ошибки
   клиентской навигации в [+error.svelte](../../src/routes/+error.svelte).
   Сохранить 401/403, request ID, no-store и безопасное поведение других отказов.
6. Показать текущую серверную роль в общей навигации. После входа/выхода и следующего
   перехода/обновления отображать актуальное состояние; не строить навигацию по
   одному факту существования browser cookie или старым данным вкладки.

Если историческое состояние сессии недоступно, отчёт отделяет воспроизведённый
механизм от предположения о конкретном прежнем входе. Успешная проверка изолированного
parent и исправленные сообщения достаточны для этого UI-пакета; не начинать
расширенное remote-расследование без нового воспроизводимого отказа.
Вывод достаточно включить в итог реализации; отдельный диагностический инструмент,
новое хранилище evidence и самостоятельный отчёт не требуются.

Не менять TTL, криптографию, модель ролей, правила ownership и namespace cookie
ради одновременной демонстрации. Не добавлять impersonation, multi-account switcher
или постоянный polling. Для ручного показа использовать отдельные browser profiles
либо обычный и изолированный приватный context; два обычных окна не изолируют вход.
Remote login/logout/revoke и массовая очистка сессий для диагностики не требуются.

## 4. PVUI-02: общая навигация и первый экран

- Общая шапка: название Kolibri, «Занятия», доступный для текущей роли раздел,
  переключатель DE/RU и действия учётной записи. Parent получает «Личный кабинет»,
  «Сообщения», «Настройки»; admin — «Администрирование», «Настройки».
  Простые ссылки и кнопки достаточны; отдельное dropdown-меню не обязательно.
- Гостю доступны вход и регистрация. Восстановление пароля и повторное подтверждение
  email перенести к соответствующим auth-формам; не выводить их пятью ссылками
  над каждой страницей. Сами маршруты остаются доступны.
- Выход использует существующий защищённый POST action; никаких logout по GET.
- На каталоге, пробном, заявках, сообщениях и предложениях договоров есть ясный
  возврат в доступный кабинет/раздел. Сохраняются адреса существующих routes.
- На главной вместо заглушки показать короткое назначение портала и действующие
  переходы: выбрать занятие, открыть кабинет или войти. Не добавлять фиктивные
  показатели, карусели и рекламные обещания.
- Использовать одну визуальную систему: светлый фон, белые карточки, один основной
  акцент, единая типографика и различимые основные/вторичные действия. Использовать
  существующие зависимости и иконки; новый UI framework не нужен.

Серверный layout передаёт только минимальное состояние для навигации. Не отдавать
в browser `AuthenticatedUser` целиком, sessionId, csrfHash или токены. Проверить,
что зависящая от пользователя шапка не попадает в общий кэш и обновляется при
обычной навигации после смены входа.

## 5. PVUI-03: компактный кабинет

Рекомендуемый порядок: заголовок и быстрые действия → «Требует вашего действия»
при наличии таких объектов → занятия → дети → заявки/пробные → договоры и история
→ сообщения → профиль/служебные настройки. Вверху дать переходы к разделам.

- Быстрые действия: «Выбрать занятие», «Добавить ребёнка», «Написать в бюро».
- В блоке внимания использовать уже загружаемые данные: доступное предложение
  договора, требующее ответа изменение цены, запрос дополнительных сведений.
  Не объявлять каждый открытый объект срочным и не добавлять новые фоновые запросы.
- Дети по умолчанию представлены карточками; форма появляется по «Изменить».
  Добавление ребёнка раскрывается отдельно. Ошибка отправки сохраняет значения
  и оставляет нужную форму открытой. Legacy correction не становится прямым edit.
- «Всё равно сохранить» показывать в контексте реального предупреждения о дубликате,
  с понятным пояснением; сохранить существующую серверную проверку и явное подтверждение.
- Пустые разделы имеют короткий текст и доступное следующее действие. История и
  профиль могут сворачиваться; обязательные предупреждения и ожидающие действия — нет.
- Действующие услуги, предложения и история договоров остаются различимыми.
  Сумма сохраняет смысл ориентировочной базовой стоимости по `CAB-02`.

При 1366×768 верхний экран показывает назначение кабинета и быстрые действия;
при наличии требующего ответа объекта его блок виден до форм профиля/детей.
Высота страницы не должна достигаться ценой потери существующих разделов.

## 6. PVUI-04: каталог и доступ к договору без пробного

- Карточка показывает предмет/название, расписание, длительность, преподавателя,
  место, доступность и цену с ясной иерархией. Не придумывать возрастные границы,
  изображения преподавателей и цены. «Цена уточняется» — честное состояние.
- Предмет можно визуально выделить над техническим названием, сохранив исходное
  название и маркировку synthetic preview. Не переименовывать записи в базе.
- Сохранить существующую кнопку пробного. Добавить для групп вторичный вход
  **«Запросить договор без пробного»** через существующее обращение категории
  `contract`: форма объясняет, что предложение подготовит администрация.
- Самый короткий вариант — предзаполнение темы/текста существующей формы по выбранному
  занятию. Перед отправкой родитель может их изменить. GET/переход ничего не создаёт;
  отправка остаётся отдельным явным действием существующего message flow.
- Параметр занятия проверяется на сервере по доступному опубликованному каталогу.
  Имена, контакты и произвольный текст не передаются через URL. Некорректный параметр
  даёт безопасное объяснение или обычную форму без ложного предзаполнения.
- На странице договоров кратко объяснить существующий порядок по `CONTRACT-01`.
  Новый запрос не является предложением договора, не резервирует место и не означает
  принятия условий. Создание offer и его жизненный цикл сохраняются.

Это ограниченное дополнение навигации, без новой таблицы заявок и без мастера
административного договора. В scope нет автоматического переноса обращения в offer.
Обновить `CAT-03` и соответствующий критерий при реализации. В preview агент
проверяет открытие/предзаполнение формы, не нажимая отправку.

## 7. PVUI-05: формы, размеры и адаптивность

- Общие правила box-sizing, `min-width: 0` для элементов сеток, ограничение ширины
  полей, перенос длинного текста. Не маскировать переполнение общим `overflow: hidden`.
- Ориентиры desktop: дата 12–14rem, короткое число 6–10rem, имя/тема 24–36rem;
  на узком экране поле ограничено доступной шириной. Описание занимает строку
  формы, имеет разумную минимальную высоту и вертикальное изменение размера.
- JSON в существующей технической форме договора получает широкую строку и
  моноширинный шрифт. Это исправление геометрии, а не разработка нового редактора.
- Поля поиска и фильтры имеют связанные labels, выравнивание и перенос. Таблица
  при необходимости прокручивается внутри своего контейнера, не всей страницы.
- Кнопки удобны для касания (ориентир 44 px); видимый focus, логичный Tab-порядок,
  корректные label/fieldset/legend, inline errors и связь через aria-describedby.
- Раскрытие секции, поиск, смена языка и обычный переход не отправляют business form.
  При скрытии формы не оставлять невидимые required-поля блокирующими другую форму.

Основной визуальный проход: 390×844 и 1366×768. На 768×1024 и 1536×864 проверить
перекомпоновку тех же страниц изменением viewport, без повторных входов и бизнес-сценариев.
Поддержка промежуточных размеров сохраняется. На 390 px ширина документа не превышает
viewport, все основные действия доступны. После осмотра восстановить viewport владельца.

## 8. PVUI-06: административная навигация и списки

- Сгруппировать существующие ссылки и обозначить текущий раздел. Компоновку выбрать
  по существующей разметке: компактное меню с переносами или боковая панель.
  На мобильном сохранить удобный доступ к группам без чрезмерной высоты шапки;
  раскрытие можно сделать штатным элементом, без отдельной системы меню.
  Группы: «Семьи и обращения», «Занятия и договоры», «Данные и система».
- Сохранить все существующие разделы и права. Добавить на обзор быстрые переходы
  к повседневным операциям. Новая аналитика и запросы подсчёта всех сущностей не нужны.
- По решению владельца от 2026-09-15 оставить существующий счётчик
  «Заблокированные учётные записи» без кликабельного перехода. Рядом дать отдельную
  ссылку **«Все учётные записи»** на `/admin/users` без фильтра `status=active`.
  Значение счётчика и существующие поиск/фильтры списка сохраняются. Новый серверный
  фильтр блокировки и переход только к заблокированным аккаунтам отложены.
- В каталоге отделить занятия от сопоставлений. Сопоставления по умолчанию свернуты,
  с числом уже загруженных элементов. Сохранить возможность открыть каждую запись;
  не объединять разные объекты из-за одинакового названия `Synthetic Old Group`.
- В существующих списках показывать сначала сущность, понятный статус и действие;
  форму изменения раскрывать по запросу. Сохранить поиск/фильтры, подтверждения и audit.
  Сначала применить общие стили; отдельную разметку менять там, где они не решают
  обнаруженную проблему. Переписывание всех списков в новый общий компонент не требуется.
- Технические реквизиты и JSON — в подробностях, но не прятать предупреждения,
  необходимые для принятия решения. Пустые таблицы объяснять текстом.

## 9. PVUI-07: язык, статусы и сообщения

- Одинаково завершённые DE/RU: общая навигация, новые действия, ошибки, empty states.
- Переводить известные коды категорий и статусов через существующий i18n.
  Свободную переписку, исходные названия и диагностические идентификаторы не переводить.
- Timestamps отображать локализованно в `Europe/Berlin`; calendar-date поля
  форматировать как дату без сдвига timezone. В базе и form payload значения прежние.
- Цвет статуса сопровождается текстом. «Готов PDF», «Ожидает принятия родителем»
  и «Договор действует» не сводятся к одному неоднозначному «Готово».
- Юридические тексты согласия, версии и hashes не редактировать для красоты;
  немецкий оригинал и существующий русский перевод сохраняются по `UI-01`.

## 10. Реализация и проверка

Первый видимый результат — общая навигация, исправленные размеры и компактный
кабинет. Диагностику 403 выполнить в начале, но не превращать поиск исторической
cookie в условие начала независимых UI-правок. Подтверждённый P0/P1 обрабатывается
по правилам репозитория. Затем — каталог, списки и локализация; связанные изменения
получают один focused regression run после завершения пакета.
Не начинать соседние refactoring, provider recovery или подготовку новых данных.
Если для пункта понадобятся новая схема данных, замена auth-механизма или общий
workflow engine, остановить расширение именно этого пункта и согласовать новый
объём с владельцем. Остальная независимая работа продолжается.

Основные точки изменений: `src/app.css`, root layout/page/error, `AuthNav.svelte`,
`LanguageSwitcher.svelte`, `src/lib/i18n`, `src/hooks.server.ts`,
`src/lib/server/i18n/error-response.ts`, страницы кабинета, каталога, сообщений и
администрации. Повторяемую навигацию/поля можно вынести в небольшие общие компоненты.
Изменение session storage, migrations, dependencies и deployment config не ожидается.

| Проверка | Критерий готовности |
| --- | --- |
| Один и два browser contexts | Результат минимального воспроизведения 403 описан, историческая гипотеза отделена от фактов; штатный отказ роли сохранён; действующий parent в изолированном context открывает свои страницы |
| 401/403, прямой GET и клиентская навигация | Правильные HTTP-коды, DE/RU-пояснения и доступный следующий переход; нет ложного сообщения о пароле |
| Гость / parent / admin | Шапка соответствует текущему серверному входу; каталог и нужный кабинет связаны; нет вывода session secrets |
| Кабинет с пустыми и заполненными данными | Все существующие функции доступны; важное действие выше форм; раскрытие/ошибка формы работают |
| Каталог → пробное / запрос договора | Нужная существующая форма открывается; выбранное занятие не теряется; переход не создаёт записей |
| Геометрия | Нет переполнения документа на 390 px; нет растянутых дат и узких многострочных описаний; таблицы скроллятся локально |
| Админские списки | Меню удобно на двух классах экранов; сопоставления доступны; счётчик заблокированных не является ссылкой, отдельная ссылка «Все учётные записи» открывает `/admin/users` без предустановленного фильтра |
| Локализация и доступность | DE/RU, сохранение языка, клавиатура, focus, labels, понятные ошибки и локальные даты |
| Сохранность поведения | RBAC/ownership/CSRF и идемпотентность непосредственных затронутых действий сохранены; реальные providers не вызываются |

Выбор тестов пропорционален изменениям по [AGENTS.md](../../AGENTS.md):

- Для документа подготовки: `npm run docs:check`, `npm run release:scan`, проверка
  diff и новых файлов. Runtime suite сейчас не нужен.
- При реализации: `npm run check`; targeted auth/session/role, i18n, cabinet/catalog/
  messages/admin suites по фактическому diff; affected Chromium scenarios.
  Ориентиры существующих файлов: `tests/unit/auth-security.test.ts`,
  `tests/unit/parent-product-route-security.test.ts`, `tests/unit/i18n.test.ts`,
  `tests/e2e/authenticated-access.spec.ts`, `tests/e2e/00-ui-language.spec.ts`,
  `tests/e2e/catalog-trial-lifecycle.spec.ts`, `tests/e2e/accessibility.spec.ts`.
  Это указатели на существующее покрытие, не команда запускать каждый файл целиком.
  Дополнить только недостающие проверки реального поведения, не снимками CSS-классов.
- Browser smoke: главная, каталог, кабинет, пробное, новая individual/Nachhilfe
  форма, сообщения, настройки, admin overview/catalog/contracts/pricing.
  Один визуальный проход по этим страницам на уже подготовленном состоянии;
  не перемножать все routes × роли × языки × размеры × способы навигации.
  Роли проверяются в PVUI-01/02, размеры — в PVUI-05; не дублировать те же проверки
  отдельными сценариями в каждом пункте. Проверку DE/RU совместить с этим проходом.
  Playwright/Chromium — основной инструмент; Computer Use только когда более
  лёгкое подключение не даёт нужного наблюдения, без повторного аудита всей системы.
  На существующих договорах проверять только затронутый UI. Не создавать новую
  remote семью и не скачивать чувствительные документы ради скриншота.
- Локальные тесты могут использовать синтетические fixtures и изолированные
  transport substitutes; это не доказательство полного preview lifecycle.
- Перед отдельно разрешённым deploy применять release-матрицу репозитория.
  Для ожидаемых общих runtime/навигационных изменений сохранить полный `npm test`,

  CSS-изменения, read-only осмотра или docs-only commit.
  Автотесты не должны обращаться к реальным provider targets; если изоляция не
