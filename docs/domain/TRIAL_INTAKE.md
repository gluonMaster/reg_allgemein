# Короткая заявка на пробное занятие

Дата: 2026-09-16. Статус: **ТЗ согласовано по продуктовым решениям OQ-037–043/045–047;
локальный release gate 03 завершён; deployment и реальные provider gates впереди**.

Этот документ задаёт отдельный ограниченный release `trial-intake` по срочному
поручению владельца. Deployment требует отдельного прямого поручения.
Подтверждённый scope и решения зафиксированы в
[OPEN_QUESTIONS](../spec/OPEN_QUESTIONS.md). Технические параметры ниже —
предлагаемые defaults реализации; они не расширяют продуктовый объём.
План реализации: [TRIAL_INTAKE_RELEASE_TZ](../implementation/TRIAL_INTAKE_RELEASE_TZ.md).

## Подтверждённый результат

- **TIN-01.** Из карточки реального опубликованного расписания родитель переходит
  на портал и подаёт запрос на пробное. Передаются предмет, группа, день недели,
  время, преподаватель, кабинет и здание. Сбор персональных данных происходит
  на портале. Канонический источник расписания — HTML визуализатора; копия
  каталога полного портала не является предпосылкой этого release.
  Поддержка записи реализуется в исходниках и сохраняемой конфигурации
  визуализатора редактора `C:\path\to\schedule-editor`.
  Каждый штатный экспорт после редактирования расписания заново создаёт
  каталог и ссылки по TIN-06. Netlify хранит результат этого экспорта;
  ручные правки опубликованного/скачанного HTML и отдельный post-processing
  вместо доработки экспортера не допускаются (OQ-046).
- **TIN-02.** Обязательные данные: отдельные имя и фамилия родителя, телефон,
  email, отдельные имя и фамилия каждого ребёнка и его дата рождения. Нужны
  один или несколько детей. Цель — удобная короткая форма на телефоне и компьютере.
- **TIN-03.** Для нового устройства/адреса сначала отправляется проверочное письмо.
  Повторная заявка с подтверждённого устройства для того же адреса принимается
  сразу по правилам раздела «Повторная заявка с того же устройства» ниже.
  Только после подтверждения
  email запрос поступает в рабочий список администратора и создаёт Telegram-
  уведомление. Подтверждение email не подтверждает место или дату посещения.
- **TIN-04.** По прямому уточнению владельца Telegram содержит всю заявку:
  контакты родителя, имена/фамилии и даты рождения детей, выбранные для них
  занятия/даты, предмет, группа, день, время, преподаватель, кабинет, здание
  и ссылку на admin detail. В кабинете доступны эти же сведения,
  фильтрация и сортировка по предметам, преподавателям, дням недели, фамилиям
  детей и родителей. Обратная связь — ручной звонок администратора.
- **TIN-05.** В release входят только этот запрос, проверка email, доставка,
  рабочее представление заявок и необходимое администрирование. Цены, договоры,
  оплаты, загрузка документов, legacy import и расчёт вместимости не нужны для
  этого результата. Текущий pricing-пакет не является зависимостью.

## Пользовательский сценарий

1. Все опубликованные group-карточки доступны для запроса. Для первого выпуска
   принят локальный источник от 09.09.2026 с 110 карточками вместо предыдущих
   108 на Netlify (OQ-047); число карточек не зафиксировано как бизнес-лимит. В каждой
   подходящей публичной карточке есть явная ссылка
   «Probestunde anfragen / Запросить пробное». Обычная HTTPS-навигация в той же
   вкладке, без iframe. Ссылка доступна с клавиатуры и без JavaScript. Ссылка
   стоит на каждой карточке, поэтому укомплектованность группы портал сообщает
   сам, по разделу «Укомплектованные занятия» ниже.
2. На `/probestunde` предвыбрано занятие из ссылки и ближайшая дата его дня недели.
   Ниже — контакты родителя, первый ребёнок и «Ещё один ребёнок». Владелец просит
   выбор нескольких доступных занятий, каждое со своей желаемой датой.
   «Ещё одно занятие» раскрывает простой поиск/выбор из того же опубликованного
   расписания; до первого выбора та же кнопка называется «Выбрать занятие».
   Названия кнопок говорят о добавлении следующего ребёнка или занятия, а не о
   сохранении уже введённых данных. У каждого занятия галочками выбираются дети;
   по умолчанию первый ребёнок. Удаление ребёнка удаляет его назначения, но не
   оставляет незаметно выбранное занятие без детей: перед submit требуется
   исправить выбор.
3. Аккаунт и пароль не создаются (согласовано). Для каждой даты сервер проверяет
   корректную календарную дату и нужный день недели. Разрешены даты начиная с
   завтрашнего дня в Europe/Berlin; ближайшая подставляется автоматически.
   Поле желаемой даты предлагает только ближайшие шесть дат этого же дня недели,
   поэтому другой день недели нельзя выбрать в форме. Сервер остаётся источником
   правила и отклоняет чужой день недели, сегодняшнюю и прошедшую дату независимо
   от UI. Каникулы, разовые отмены, доступность мест и конфликты детского
   расписания автоматически не рассчитываются. Дата желаемая, окончательное
   посещение согласует бюро.
4. Для нового устройства/адреса после «Подать запрос» показывается экран «Проверьте почту», возможность
   повторить письмо через 60 секунд и исправить ошибочный email новой отправкой
   формы. Экран предупреждает, что доставка письма может занять до 5 минут, чтобы
   ожидание не выглядело сбоем; о технических каналах доставки он не сообщает.
   Ошибка валидации/сети сохраняет ввод и ключ повторной операции.
5. Ссылка из письма открывает страницу с одной кнопкой подтверждения. GET ничего
   не подтверждает: это защищает от случайного подтверждения почтовым сканером.
   POST подтверждает и показывает, что заявка принята и детали отправлены письмом.
6. При обычной проверке клиент получает два письма с разными ролями, при повторной
   заявке с подтверждённого устройства — только подтверждающее, см. «Письма клиенту» ниже.
   Уведомления после ручной обработки нет; кабинета родителя и восстановления
   гостевого профиля тоже нет.
   Повторное открытие успешно использованной ссылки сообщает об
   уже принятом запросе без повторного уведомления и без раскрытия контактов.

**OQ-038 решён:** форма DE/RU, немецкий по умолчанию; письма только по-немецки.
Новый текст сначала согласуется с владельцем на русском, затем переводится.
Смысл общих старых email/Telegram текстов по UI-01 сохраняется;
написание названия учреждения уточняется следующим правилом.

### Повторная заявка с того же устройства

Решение владельца от 2026-09-22: после успешного POST `/probestunde/verify`
браузер получает host-only cookie `ti_verified` на 180 дней, с `HttpOnly`,
`Secure`, `SameSite=Lax`, `Path=/probestunde`. GET cookie не выдаёт.
Cookie содержит только нормализованный email и HMAC-SHA256 на `JWT_SECRET`
с областью `trial-intake:device:v1`; имён, детей и ID заявки в нём нет.
Срок задаётся браузеру через Max-Age; timestamp внутри подписанного значения нет.

При submit сервер проверяет подпись и совпадение адреса с нормализованным email
формы. Подходящий cookie позволяет сразу принять заявку как `verified`:
одна транзакция фиксирует `verified_at`, Telegram-payload/outbox и ровно одно
подтверждающее письмо. Проверочное письмо для этой новой заявки не создаётся,
неиспользуемый verification token никому не выдаётся. Повтор отправки не
дублирует уведомления; после сбоя транзакции приёма тот же submit может завершить
сохранённую pending заявку. Успешный экран сообщает о письме с деталями, без
resend и исправления email. Turnstile и оба submit rate limit сохраняются.

Без cookie, с повреждённой/чужой подписью или другим адресом действует обычная
верификация. Наличие email в базе само по себе никогда не даёт освобождения:
это позволило бы подавать чужие заявки и узнавать о семьях перебором адресов.
Cookie подтверждает ранее проверенную почту в браузере, не личность человека
за общим компьютером; он не предоставляет чтение заявок или семейных данных.

После успешного submit браузер сохраняет только имя, фамилию, email и телефон
родителя в `localStorage` под `trial-intake:parent:v1`, до очистки пользователем
или браузером. При открытии формы они заполняют только пустые поля; дети,
занятия и receipt не сохраняются. «Это не мои данные» очищает запись и контакты
в форме, оставляя cookie: другой email всё равно требует подтверждения.
Недоступное или повреждённое хранилище не мешает отправке. Серверного профиля
гостя и подстановки контактов/детей по адресу из базы нет.

### Название учреждения и клиентские тексты

Во всех упоминаниях учреждения используется только полное название
**Kinder- und Elternzentrum "KOLIBRI" e.V.**, одинаковое для DE и RU.
Правило включает шапку, заголовки страниц, формы, admin UI, тему/тело/подпись
письма, отображаемое имя отправителя и Telegram. В доступных на этом release
общих login/reset/recovery экранах и письмах название также должно быть полным.
В каждом приложении название хранится одной константой, а не отдельными
переводами или сокращениями.
Кавычки и завершающее `e.V.` сохраняются; длинное название переносится на мобильном
экране без обрезания. Смысл старых шаблонов не меняется из-за исправления названия.

Машинные ключи зданий, имена файлов, URL и resource IDs сохраняют свой контракт.

Название здания — не упоминание учреждения, а обозначение адреса занятия рядом с
номером помещения. Там, где показано именно здание, остаются короткие маркеры
`Kolibri` и `Villa`: карточка экспортированного расписания, карточка занятия в
форме и подтверждении, фильтр и список admin UI. Подстановка полного названия
вместо ключа `Kolibri` сохраняется только в письме и Telegram, где строка занятия
читается вне контекста портала. Подпись не меняет ключ или ID занятия.

Полное название остаётся в шапке портала и экспортированного HTML, в заголовках
страниц, теме и подписи письма, имени отправителя и admin UI вне поля здания.

### Письма клиенту

Решение владельца от 2026-09-22 после консультации с бюро: клиент получает два
письма при обычной верификации, каждое со своей ролью; подтверждённое устройство
для того же email получает только подтверждающее. Прежняя формулировка «второго письма нет»
(OQ-042) этим заменена.

**Проверочное письмо** уходит сразу после отправки формы и остаётся коротким:
что запрошено, кнопка подтверждения и предупреждение, что заявка ещё не является
подтверждением места. Оно не обещает звонка и не говорит, что клиент записан:
до нажатия кнопки заявка в бюро не поступает.

**Подтверждающее письмо** уходит после подтверждения адреса и сообщает, что
запись принята: по строке на занятие с именами записанных детей, предметом,
группой, днём недели и датой, временем, зданием, его адресом и кабинетом. Затем
«при необходимости мы свяжемся с вами», телефон и полное название учреждения.

Адреса зданий в клиентских текстах: `Kolibri` —
Ritzenbergstraße 3 • 01067 Dresden, `Villa` — Kraftwerk Mitte 2 • 01067 Dresden.
Телефон — +49 179 9474938. Они хранятся одной константой рядом с названием
учреждения, а не повторяются по шаблонам. Письма остаются только немецкими.

Повторное открытие подтверждающей ссылки второго письма не создаёт. Очередь
писем различает эти два типа, поэтому отмена устаревшего проверочного письма
не трогает подтверждающее.

### Укомплектованные занятия

Заполненные группы не принимают заявки, но расписание — отдельный проект и про
вместимость не знает. Поэтому закрытие живёт на портале: администратор отмечает
занятие, и запись на него прекращается без правки расписания и без deploy.

Ключ отметки — **предмет, группа и день недели**, без времени. Решение владельца
от 2026-09-22: время меняется часто, и отметка не должна теряться из-за него.
Отметка переживает смену времени, кабинета, преподавателя и здания. Ключ группы
самой по себе недостаточен: одно название покрывает разные занятия — `1B` это и
Russisch, и Kunst, `3J Russisch` идёт в двух зданиях в разные дни. `lesson.id`
для этого тоже не годится: он включает преподавателя и кабинет и меняется при
обычной правке расписания. На каталоге от 2026-09-22 принятый ключ даёт 110
уникальных значений на 110 занятий. Если одна группа по одному предмету однажды
пойдёт дважды в один день, отметка закроет оба занятия; админ-страница показывает
число затронутых занятий, поэтому это видно сразу.

Посетитель, пришедший по ссылке на закрытое занятие, видит вместо формы короткое
сообщение, что группа укомплектована, кнопку возврата к расписанию и возможность
выбрать другое занятие на портале. Закрытые занятия не появляются в поиске
занятий, и сервер отклоняет их при отправке заявки: проверка формы не является
достаточной защитой от прямого POST.

Отметку ставит и снимает обычный администратор на странице «Укомплектованные
занятия»; оба действия попадают в audit log. Записи, переставшие совпадать с
текущим расписанием, показываются отдельно и удаляются вручную. Каталог и его
JSON остаются без изменений: закрытие — состояние портала, а не расписания.

### Навигация портала

Шапка предлагает только переходы, ведущие в другое место. На самой `/probestunde`
ссылки на эту же форму нет, администратору она не показывается вообще, а вход для
бюро вынесен из шапки в подвал рядом с Kontakt/Datenschutz. Ссылка на консоль
исчезает из шапки внутри `/admin`, где та же навигация уже есть. Выход
администратора остаётся в шапке. Сам маршрут `/auth/login` не меняется.

Клиентские экраны и письма этого контура не сообщают о Telegram или других
технических каналах доставки. Короткий текст у формы содержит только сроки
удаления по TIN-12; внутренние настройки доставки остаются в operator документации.

## Контекст занятия

- **TIN-06.** Для выбора нескольких занятий экспортер помещает в тот же HTML
  `<script type="application/json" id="trial-intake-catalog">` с точным envelope
  `{"version":1,"lessons":[...]}` и массивом только публичных полей
  `id, subject, group, weekday, start, end, teacher, room, building`.
  `weekday=1..7`, время `HH:mm`, внутренний ключ здания `Kolibri|Villa`.
  Человеческие подписи зданий формируются по правилу названия учреждения выше.
  ID — lower-case SHA-256 от UTF-8 compact JSON массива
  `[subject, group, weekday, start, end, teacher, room, building]` после trim и
  NFC строк; порядок фиксирован, weekday integer, пробелы JSON не добавляются.
  Одинаковое
  название с разными днями/временем/местом/преподавателем даёт разные ID.
  Общая synthetic fixture reader/exporter:
  [catalog-v1.json](../../tests/fixtures/trial-intake/catalog-v1.json).
  Непустые текстовые поля ограничены 160 символами; `end > start`.
  Byte-identical повтор одной визуальной карточки не создаёт второй выбор.
  Ссылка в CTA: `/probestunde?lesson=<id>`. JSON экранирует `<`, чтобы исходные
  строки не могли закрыть script element. Секретов в HTML нет.
  В JSON входят только реально выводимые публичные group-карточки этого экспорта;
  внутренние, скрытые и индивидуальные строки редактора в него не попадают.
  Предмет берётся из `lesson.subject`, день — из внешнего цикла экспортера;
  название субколонки «Samstag (1/2)» не является отдельным днём недели.
- Сервер портала получает JSON из фиксированного HTML URL конфигурации. Это
  извлечение одного versioned JSON-блока, без разбора визуального DOM. URL не
  берётся из запроса, reader отклоняет любые redirects; timeout 5 секунд,
  чтение до 1 MiB, до 500 записей, schema validation и краткий cache до 5 минут.
  Новые submission IDs проверяются по этому списку; названия и место сервер
  берёт из него, не из hidden fields. При недоступном/невалидном источнике и
  отсутствии свежего cache форма сохраняет ввод и предлагает повторить.
  После verification расписание повторно не запрашивается: уже принятый snapshot
  сохраняет смысл заявки даже при изменении источника.
- Предлагаемые технические пределы формы: до 16 KiB, каждое текстовое поле до
  160 символов, 1–10 детей и 1–10 занятий. Эти пределы применены в сервере 01.
  Один и тот же lesson ID выбирается один
  раз с одной датой; минимум один ребёнок на выбранное занятие. Возрастных правил
  зачисления, корзины между сессиями и сложного календарного компонента нет.
- В ссылке нет родительских/детских данных, email, телефона, токенов и секретов.
  Origin портала задаётся в конфигурации экспортера, не принимается от посетителя.
  Redirect/return URL из произвольного входа не выполняется.
- Сервер сохраняет snapshot выбранных полей вместе с заявкой. Нет общей базы
  редактора и портала, D1-импорта расписания или второго deployment при каждом
  изменении расписания. Один новый HTML содержит карточки, ссылки и каталог.
- Portal origin и переключатель показа CTA сохраняются в конфигурации редактора
  и используются обычным действием экспорта из веб-редактора. После первого
  включения следующие экспорты сохраняют поддержку записи без правки HTML.
  Достаточно параметров существующей конфигурации; отдельный экран настроек
  или новая система публикации для этого не требуются.
  Первоначальный режим «каталог без CTA» и последующее включение ссылок также
  получаются экспортом с соответствующей настройкой. Приёмка включает повторный
  экспорт после изменения synthetic занятия: карточка, каталог и ссылка
  согласованно обновляются, поддержка записи сохраняется.
- Принятый snapshot не переписывается при изменении расписания. Старая сохранённая
  ссылка с исчезнувшим ID не подменяется похожим занятием: форма просит выбрать
  актуальное из каталога. Администратор сверяет выбранную дату перед звонком.
- Нет fuzzy сопоставления с course/session ID полного портала. Отсутствующий
  предмет нельзя угадывать по первому слову группы: экспортер сообщает оператору
  о неполном контексте. Неверная ссылка открывает понятную ошибку и переход обратно
  к расписанию; пустой запрос без выбранного занятия не отправляется.

## Сохранение и подтверждение

- **TIN-07.** Отдельные intake-записи не создают `users`, canonical `children`,
  FamilyID, enrollment или обычный `trial_request`. Совпавший email с аккаунтом
  полного портала не связывает данные и не открывает доступ к нему.
- Состояния: `pending_email → verified → processed`. Истечение verification token
  не создаёт отдельного business state: resend возможен до общего 14-дневного TTL
  заявки. Отметка processed обратима в verified и означает завершённый ручной
  контакт, не зачисление (OQ-041).
- Создание заявки, списка детей и задания проверочного письма — одна D1 batch-
  транзакция. Повтор с тем же idempotency key и тем же содержимым возвращает
  прежний результат; с другим содержимым отклоняется. Новый сознательный запрос
  допустим: не строить дедупликацию семей по именам и датам рождения.
- Verification привязана к конкретной заявке и версии её email. Предлагаемый TTL
  24 часа; resend cooldown 60 секунд. В базе только hash проверочного токена;
  письмо может восстанавливать токен из отдельного scoped HMAC и случайного nonce.
  Resend отменяет предыдущую версию и её ещё не отправленное письмо. Все проверки
  срока и текущей версии выполняются также при dispatch и при подтверждении.
- Успешное подтверждение и постановка одного логического Telegram-уведомления
  происходят атомарно. Оно может состоять из нескольких частей по TIN-09.
  Повтор/конкурентный POST не создаёт вторую заявку или повторный комплект частей.
  Сбой Telegram не откатывает verified-заявку и не прячет её от администратора.
- Письмо/публичная квитанция не включают даты рождения и полный состав детей.
  Публичного чтения заявки по ID нет. Verification URL не даёт права просматривать
  сведения о семье. Confirmation/resend работают без аккаунта, но требуют
  соответствующий scoped token/receipt и серверные ограничения частоты.

## Администратор и доставка

- **TIN-08.** Предлагаемые `/admin/trial-intake` и detail route используют текущую
  серверную admin role/session, CSRF и audit. На главном экране — новые verified
  заявки, самые свежие сверху. Фильтры комбинируются: предмет, преподаватель, день,
  здание, обработано/не обработано; отдельный поиск по фамилии родителя/ребёнка.
  Сортировка в обе стороны по предмету, преподавателю, дню+времени, фамилии родителя,
  фамилии ребёнка и времени поступления. Всегда есть устойчивый tie-break по ID.
- В списке одна строка/карточка на выбранное занятие, связанная с общим номером
  заявки; внутри перечислены относящиеся к нему дети и желаемая дата. Фильтр
  по ребёнку находит строку по любому назначенному ребёнку, сортировка — по первой
  фамилии по алфавиту. Detail показывает заявку целиком. Отметка «Обработать всю
  заявку» явно относится ко всем её занятиям, а не к одной строке (OQ-041).
  Серверная пагинация по 50 строк; SQL sort keys выбираются из allowlist.
- Детали показывают все введённые поля, snapshot занятия, время подтверждения,
  состояние доставки и действие «Обработано». `tel:` и `mailto:` облегчают ручной
  контакт. Заметки, назначения операторов, календарь, CSV и переписка не обязательны.
- Рабочий список содержит только подтверждённые заявки. Технический счётчик
  неотправленных проверочных писем и recovery доступны администратору; pending
  данные не объявляются входящей подтверждённой заявкой.
- **TIN-09.** Новое Telegram template использует существующие outbox, Cron,
  Bot API adapter и manual recovery. Точный payload allowlist расширяется только
  для нового template: полный состав TIN-04 явно разрешён владельцем (OQ-039).
  Внутренние audit/evidence/logs при этом по-прежнему не содержат PII.
  Рабочее окно сохраняется: фактическая согласованная конфигурация текущего
  preview переносится в production; проектный default Mo–Fr 09:00–17:00 Berlin.
  После verification заявка видна в админке сразу, Telegram вне окна ждёт.
- Обычная заявка — одно сообщение. Длинная разбивается по строкам на части без
  потери данных; каждая содержит reference, номер части, admin link и delivery
  reference. Общая длина каждой части не превышает existing provider limit 4096
  символов; резерв под обрамление учесть до split. Дедупликация и retries отдельны
  для каждой части; номера позволяют собрать сообщение при любом порядке доставки. Частичная
  доставка видна в admin, уже отправленные части повторно не отправляются.
  Лимит подтверждён [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).
- Повторная постановка дедуплицируется. Уже реализованные `delivery_unknown`,
  backoff, блокировка проблемной destination и ручное восстановление сохраняются;
  обещание exactly-once внешней доставки не даётся. Новый bypass рабочего окна
  и переписывание provider adapter не требуются.
- Уведомление заявки ждёт только неподтверждённую часть своей же заявки.
  Неоднозначность или отказ (`dead`) любого другого сообщения его не
  останавливают (решения владельца 2026-09-23 и 2026-09-24). Поводом стали
  production-случаи: неподтверждённая отправка дважды молча останавливала
  уведомления о следующих заявках. Правило и его обоснование — в
  [MESSAGING](MESSAGING.md#telegram-bot-api-provider); автоматический повтор
  неизвестного сообщения по-прежнему не выполняется.
- Когда уведомление заявки получает `delivery_unknown` или `dead`, портал один
  раз пишет об этом на почту бюро `registration@kolibri-dresden.de` (решение
  владельца 2026-09-24): Telegram не может сам сообщить, что он не сработал.
  Письмо на немецком содержит только код доставки, номер части, код ошибки,
  короткую инструкцию и ссылки на заявку и страницу доставки. Данных заявки в
  нём нет. Письмо ставится в очередь в той же операции, которая переводит
  уведомление в это состояние, — при любом пути: ответ воркера, сверка
  зависшей отправки, исчерпание попыток. Повторный сбой того же уведомления
  после разрешённого админом повтора даёт новое письмо.
- Администратор проверяет неоднозначную доставку по коду: открывает чат бюро и
  ищет код `TG-…` в последней строке сообщения («Zustellung: …»). Нашёл —
  «Сообщение найдено»; не нашёл — «Сообщение не найдено», и сообщение уйдёт
  повторно. Решение за администратора никто не принимает: оно требует заглянуть
  в чат. Пока есть уведомление в `delivery_unknown` или `dead`, список заявок
  показывает заметное предупреждение со ссылкой на страницу доставки.
- Карточка уведомления на странице доставки называет шаблон человеческим
  языком и показывает контекст заявки: фамилию родителя, предметы, время
  поступления и ссылку на заявку. Остальные данные остаются на странице заявки;
  удалённая по сроку хранения заявка так и помечается. Времена постановки,
  попытки и отправки даны по Берлину с названием зоны. Ожидающая карточка
  называет причину: рабочее окно бюро, решение по сообщению той же заявки или
  повтор после ошибки. Отправка, отложенная вне рабочего окна (`retry` без
  попыток), описывается как ожидание рабочего времени, а не как сбой. Отмена
  ожидающей отправки остаётся второстепенным действием.
- Проверочное письмо использует существующий Resend adapter и `EmailOutboxWorker`
  с небольшим intake-store adapter. Текущая `email_outbox.recipient_user_id NOT NULL`
  исключает прямое подключение гостя. Не создавать фиктивные аккаунты, не
  перестраивать старую таблицу ради гостевых адресов, не дублировать provider engine.

## Минимальная защита и жизненный цикл

- **TIN-10.** Достаточный набор: HTTPS; server validation/escaping; ограничение
  размера; existing Turnstile Siteverify на submit; rate limit отдельно по
  псевдонимизированным IP и email; cooldown resend; одноразовое подтверждение;
  admin authorization/CSRF; no-store/no-referrer; audit без контактов/детских данных.
  CAPTCHA на каждое открытие страницы, SMS, родительский пароль, device fingerprint,
  отдельный WAF-проект и новая система ролей не требуются.
- **TIN-11.** Согласованы отдельный production Worker и D1 той же codebase.
  По уточнению владельца новый контур хранится отдельным модулем репозитория:
  `src/lib/trial-intake/` содержит его логику, UI, переводы и delivery adapters;
  серверные файлы используют суффикс `.server.ts`. Маршруты — тонкие обёртки.
  Общие auth/outbox/security primitives переиспользуются через узкие подключения;
  бизнес-модули полного портала не зависят от intake. Раскладка и deployment
  config заданы в [плане](../implementation/TRIAL_INTAKE_RELEASE_TZ.md#изоляция-в-репозитории).
  `PORTAL_MODE=trial_intake` с default `full` ограничивает маршруты на
  сервере: форма/подтверждение, язык/локальное privacy notice, admin login/logout/
  reset, intake, outbox/recovery и минимальные operations. Недостаточно скрыть
  ссылки. Public registration и остальные бизнес-маршруты закрыты.
  Существующий `AUTH_PUBLIC_ENABLED` нельзя просто выключить: он выключает и login.
  Отдельный intake accepting flag останавливает новую подачу понятным maintenance
  экраном, сохраняя заявки и admin. Для инцидента с доставкой дополнительно
  используется existing scheduled-jobs stop. Конкретные имена/команды и порядок
  остановки проверяются в release packet; первый deploy не требует выдуманной
  предыдущей Worker version в новом target.
- В этом режиме нужны D1, assets, secret для session/token, Turnstile, Resend,
  Telegram и Cron. R2/Browser/legacy/pricing не нужны. Освобождение от R2/Browser
  binding requirements ограничивается этим mode; full-mode проверки сохраняются.
  Scheduler не обращается к неиспользуемым storage/contract/import paths.
- Публичный адрес — обычный HTTPS `workers.dev`, отдельный домен не покупается.
  Точное свободное имя выбирается при preflight и фиксируется в deployment manifest.
  Preview сохраняет свой Access и данные. По OQ-040 переиспользуется текущий
  Telegram bot и его bureau destination, если read-only preflight подтверждает
  правильный закрытый чат/права. Это явное исключение только для этого release
  из требования разных preview/production bots. Новый secret binding production
  получает credential через protected канал; в логи/документы token не копируется.
  Состояние очередей остаётся в разных D1; production link/reference отличимы.
  При фактической невозможности reuse остановить только Telegram enablement и
  дать владельцу пошаговую инструкцию создания чата/бота; не создавать их молча.
  Реальные
  родители не проходят Access-login. Production admin использует собственную
  известную владельцу учётную запись; перенос preview passwords/sessions запрещён.
  Первый admin создаётся контролируемой CLI-процедурой с существующим password/
  session/bootstrap кодом, одноразовой проверкой и audit. Нельзя для bootstrap
  втягивать legacy import или ослаблять обычный family-verification flow.
- **TIN-12.** У кнопки отправки показывается короткий текст о сроках ниже, без
  отдельной обязательной галочки. При submit сервер сохраняет версию показанного
  текста; отдельный workflow согласий не создаётся. Согласованы сроки:
  неподтверждённые удаляются через 14×24 часа от создания (resend не продлевает),
  подтверждённые — через 90×24 часов после отметки processed. Ещё не обработанная
  verified заявка остаётся рабочей; её срок не отсчитывается от отправки.
  Снятие processed снимает дату планового удаления до повторной обработки.
  Manual privacy request доступен через бюро. Это продуктовая политика.
  Нельзя автоматически применять бессрочный contract archive retention.
  Bounded cleanup в существующей maintenance cadence при первом успешном запуске
  после порога удаляет request/children/items/назначения,
  verification и PII в обеих очередях; unsent jobs отменяются перед удалением.
  In-flight delivery сначала завершается/reconciles и не получает данные после
  заявленного удаления. Остаётся минимальный audit без контактов и payload.
  Backups ограничены штатным retention; после restore повторно выполняется cleanup.
  Для новых сообщений того же закрытого Telegram-чата владелец одобрил штатное
  автоудаление через 14 дней (OQ-043); настройку проверить перед первым реальным
  уведомлением. Старую историю preview не удалять. Удаление D1 не объявляется
  удалением внешних копий. Не обещать Bot API purge старше 48 часов:
  [ограничение deleteMessage](https://core.telegram.org/bots/api#deletemessage).

## Серверный интерфейс шага 01

Тонкие `+server.ts` routes возвращают JSON. POST требует `application/json` и
точный `Origin` портала; admin POST дополнительно требует session и `_csrf`.
Для JSON GET использовать `Accept: application/json`. Обычная браузерная навигация
на `/probestunde`, `/probestunde/verify`, `/admin/trial-intake` и detail открывает
HTML-страницы; route wrappers подключают UI/loaders из `src/lib/trial-intake/`.
Ответы имеют `no-store`/`no-referrer`; ошибки содержат безопасный `code`.

| Route | Контракт |
| --- | --- |
| `GET /probestunde/catalog` | `lessons`, `privacyVersion`, `accepting`, `turnstileSiteKey`, UTC `now` |
| `POST /probestunde/submit` | [IntakeInput](../../src/lib/trial-intake/contracts.ts) + `turnstileToken`; ответ `id`, opaque `receipt`, `state`, `resendAfter` |
| `GET /probestunde/verify?token=…` | Только `state=invalid|expired|confirm|accepted`, без PII и изменений |
| `POST /probestunde/verify` | `{token}`; успешный ответ `state=accepted`, cookie `ti_verified`; email в JSON не возвращается |
| `POST /probestunde/resend` | `{id,receipt}`; ответ `state` и при новом письме `resendAfter` |
| `GET /admin/trial-intake` | Query по TIN-08; `query`, `total`, `rows`, 50 item rows на страницу |
| `GET /admin/trial-intake/[id]` | Request contacts/status, children, item snapshots/assignments, delivery statuses |
| `POST /admin/trial-intake/[id]` | `{processed:boolean,_csrf}`; request-level status, `deleteAfter` |
| `GET /admin/trial-intake/email` | До 50 технических unsent/dead email jobs без контактов |
| `POST /admin/trial-intake/email` | `{id,_csrf}`; audited retry текущего неистёкшего dead email job |

Admin query names: `status=verified|processed|all`, `subject`, `teacher`,
`weekday=1..7`, `building=Kolibri|Villa`, `q`, `parentLastName`, `childLastName`,
`sort=received|subject|teacher|day|parent|child`, `direction=asc|desc`, `page`.
Фильтры комбинируются; поиск ребёнка охватывает любого назначенного этой строке.
Opaque receipt даёт только resend одной заявки, не доступ к её данным;
его и ввод формы UI сохраняет в пределах текущего сценария, не добавляет в URL/logs.
Resend во время активной отправки письма отвечает `409`: повторить позднее,
не инвалидируя уже отправляемую ссылку. Turnstile action — `trial_intake`.

Existing login/reset/outbox/recovery/operations сохранены. Logout — existing
`POST /account/security?/logout`; остальные account/business routes закрыты.
Maintenance выполняет email/security cleanup и intake retention; полного
storage/contract/import maintenance в этом режиме нет.
CLI и config: [deploy/trial-intake](../../deploy/trial-intake/README.md).
UI формы, confirmation page и admin representation добавляются на шаге 02.

## Короткий текст у формы

Русский смысловой текст:

> Без подтверждения email данные заявки удаляются через 14 дней после отправки.
> После подтверждения — через 90 дней после обработки заявки администратором.

Немецкая версия того же смысла:

> Ohne Bestätigung Ihrer E-Mail-Adresse werden die Daten Ihrer Anfrage 14 Tage
> nach dem Absenden gelöscht. Nach der Bestätigung werden sie 90 Tage nach
> Abschluss der Bearbeitung durch unser Büro gelöscht.

Срок 90 дней после отметки «Обработано» повторно подтверждён владельцем.
В выпускном пакете сверяется показ именно этой версии с реализацией TIN-12;
повторное согласование уже выбранного текста не требуется. Штатные ссылки
Kontakt/Datenschutz остаются в навигации. Состав технической доставки описан
в TIN-09/11/12 для оператора и не добавляется в клиентский текст.

## Граница готовности

Release готов после прохождения [TIN-AC](../spec/ACCEPTANCE_CRITERIA.md#короткая-заявка-tin-ac),
закрытия применимых OQ, проверки реальных писем, входа администратора и
публикации ссылок в точном Netlify schedule target. По решению OQ-044 от2026-09-16
после email verification и проверки целостной Telegram-очереди с корректным
`not_before` CTA можно включить до фактической доставки. Доставка проверяется
следующим рабочим утром; её задержка/сбой сами по себе не блокируют приём.
Рабочее окно сохраняется; заявки доступны бюро через admin UI, очередь и recovery
сохраняются. Pending delivery не записывается как passed delivery.
Это отдельный ограниченный
production GO; оно не означает готовность полного MVP или завершение SYS-04.
